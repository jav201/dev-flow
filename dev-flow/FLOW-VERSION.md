## Verify the local flow

> **Which of the two recipes below is yours depends on what you installed.** If you are holding
> the published bundle — this file beside `SKILL.md`, `commands/`, `scripts/` — the canon recipe
> immediately below **does not resolve here** and the one under *From inside a bundle* is yours;
> it is the same command `SKILL.md` step 1 gives. Read that one first and treat the canon recipe
> as the authoring home's. A reader of the 2026-09-19 publication test met the canon recipe first

```bash
cd ~/.claude && files=$(sed -nE 's/^\| `([^`]*)`[^|]*\| `[0-9a-f]{16}`.*$/\1/p' docs/FLOW-VERSION.md) \
  && printf 'derived from the table: %s files\n' "$(printf '%s\n' "$files" | wc -l)" \
  && printf '%s\n' "$files" | while read -r f; do \
       case "$f" in dev-flow-lessons/SKILL.md|dev-flow-lessons/REFERENCE.md|dev-flow/SKILL.md) f="skills/$f";; esac; \
       printf '%s *%s\n' "$(tr -d '\r' < "$f" | sha256sum | cut -d' ' -f1)" "$f"; \
     done | sha256sum | cut -c1-16
```

> **It reads the table; it does not repeat it.** Until rev20 this command carried its own
> hardcoded file list — **a third inventory**, beside the table and beside the one `V7` kept
> until rev16. rev16 removed `V7`'s copy and this file quietly kept its own, so rev19's new
> row had to be added by hand in two places. *A list maintained beside the list it was meant
> to guard* is the defect this project has now found five times, and it is the reason rev15
> made the bundle a build output rather than reconciling it a third time.
>
> **The printed file count is the point, not decoration.** The one way this can fail silently
> is the `sed` ceasing to match the table's row shape, which would yield a short list and a
> confident wrong hash. A count that reads `0 files` or `3 files` is visibly absurd; a bare
> hash is not. The command deliberately has no independent copy of the expected count either
> — that would be the fourth list.

> **`tr -d '\r'` is load-bearing, not tidiness.** rev12 hashed raw working-tree bytes, and with `core.autocrlf=true` a file git wrote at checkout has CRLF while a file an editor wrote has LF. That made `flow_hash` a property of one working tree: measured at rev13, a **fresh clone mismatched 18 of 19 files** and the aggregate came out `bfb37780aa0fa43f` instead of the declared `41144ca54e8b944a`. `V7` — whose whole job is C-45's PULL check — was red on every new machine for reasons unrelated to drift. `devflow-validate.py` normalises identically (`_norm`), so the two implementations agree by construction; if you change one, change both. **The same applies to the row parse:** the `sed` above and the tool's `_canon()` read this table with two separate regexes, and rev20 made that coupling deliberate rather than accidental. Two readers of one table is the point — a second *implementation* is what can catch the tool being edited, which is the only tampering `V7` structurally cannot see. Two *lists* would not be.

## Bumping this file

`rev` increments by **1 on every content change to any listed file** — it is an ordinal, not a semantic version; there is no meaning in the gap between revisions, only order. The date is the date of that change.

**A revision that changes only this file is legal and gets a number too** (rev20 is the first). This file is deliberately not in its own table — it cannot be, the reference would be circular — so `flow_hash` is *unchanged* across such a revision. That is not drift: no tabled file moved. Say so in the changelog row rather than leaving a reader to wonder why two revisions share a hash.

Procedure, in order — the manifest is written **last**, over final content:
1. Edit the canonical file(s) under `~/.claude/commands/`, `~/.claude/templates/dev-flow/` or `~/.claude/docs/tools/`.
2. Update the `dev-flow-lessons` catalog entry if a control changed.
3. **Regenerate the bundle** — `python docs/tools/devflow-validate.py --sync-bundle`. Do **not** copy by hand; the bundle is derived from the table above. Note that `skills/` is **a separate nested repo** (the published skills repository), gitignored by the canon repository, so its changes do **not** appear in `git -C ~/.claude status` and need their own commit and push.
4. Re-run the per-file and aggregate hashes; rewrite the table and the header block.
5. Append a changelog row.
6. Commit `claude-config` and **push**; re-mirror into `agent-skills/dev-flow/` and commit there.
