# Design-first dev-flow

Design defects are cheapest before code: on a real project (s19_app, batch-100) this flow took the MAJOR/HIGH findings on code from 8 in the code-first Inc 7 to 0–2 per increment, for about 50 % more model output. Each stage gives its goal, the practices that held on real runs, and when it is done; follow them and decide the rest. A single increment is a batch of one.

## Records

Four records define the software and are kept current:
- **User stories (US)** — from the commission, each with its id in the increment's `01-requirements.md`.
- **Requirements** — the E1 rows, under the ids the canon uses (HLR/LLR, or R-<AREA>-NNN), in the increment's `01-requirements.md`, each naming its US.
- **Test cases (TC)** — in the increment's `02-test-cases.md`, one per coverage item: one alternative of one requirement, keyed `<requirement id>/<n>`. Each gives, as ISO/IEC/IEEE 29119-3 asks, its objective ("Verify that …"), its class (*normal*, or *robustness* for an `If` row, as in DO-178C), preconditions from `While`/`Where`, inputs from `When`/`If`, the expected result as the requirement's exact values, ranges or text (ISO 26262-8 §9.4.2.2), the tests that verify it, each marked `full` or `partial`, its coverage (`covered`, `partial`, `gap`, `conflict` or `not-testable`) and its result from the test run (`verified`, `failed` or `not_run`). Acceptance tests (AT) are the black-box cases.
- **Evidence** — the RED, GREEN, mutant and capture transcripts, generated by the tools and never typed by hand, committed in git and listed in the increment's validation record. A result counts only for the commit and the platform it ran on.

The trace holds both ways: every US reaches a requirement and every requirement a test; every changed function maps to a requirement through the E1 slice. `trace_check.py`, in this skill's folder, checks these records. Everything else a stage writes (rulings, graphs, reviews, the validation record) stays in the increment's folder under `.dev-flow/` as history. Commit each stage's work when the stage ends.

## Stages

**E0 — Plan and split (batch open).** Goal: a list of increments, each small enough for one focused pass.
- The commission (the operator's written request; draft it with them if there is none) describes the user stories and the scope. A change the user sees gets a UI prototype round, with the operator's verdict, before E1.
- Estimate each increment and cap it at about 80 requirements and 40 graph nodes; split larger work along boundaries the user can see.
- Done when: the increment list gives each increment its stories, scope, order, and the interfaces it shares with the others.

**E1 — Requirements.** Goal: every requirement in scope is one EARS sentence that meets ISO/IEC/IEEE 29148 (necessary, appropriate, unambiguous, complete, singular, feasible, verifiable, correct, conforming).
- One `shall` and one response per requirement, with "the system" as the subject; split until it cannot be split, and an "only when" becomes two requirements. Use the five forms only:
  - Ubiquitous — `The system shall …` (always true)
  - Event — `When <trigger>, the system shall …` (something happens; a command option is an event)
  - State — `While <state>, the system shall …` (a lasting state of the system, never a property of the input)
  - Unwanted — `If <condition>, then the system shall …` (a defect, a missing file, a bad argument)
  - Optional — `Where <feature>, the system shall …` (a feature a build or configuration may leave out)
- Every failure path gets its own `If … then …` requirement. Alternatives in one condition must share the response.
- The statement says what can be observed, never which function, file or test does it; those belong in the slice and the graph.
- A requirement that produces a message fixes its exact text, with `<placeholders>`. Definitions hold terms and formats only; anything the system does is a requirement.
- Each requirement carries a numeric pass threshold (a count such as `3/3` when the behaviour is yes or no) and a negative control: a mutant that would turn its test RED.
- Before a requirement depends on an input — a key, a terminal feature, a system call — check that it reaches the app on the target platform.
- Done when: the scope list is written, defects in existing requirements are fixed in place (a split keeps the parent id with `.1`, `.2`), the rulings file records each change and its reason, and the slice of functions to change is named, counted and mapped to its requirements.

**E2 — Prototype as a Code-Wire graph.** Goal: the functional design exists as contracts and examples taken from the requirements, before any code. Method, extractor and lint: the Code-Wire repository (start at its README).
- The prototype is the graph only: no stubs, marks or declarations in the source. Extractor marks go only in a throwaway worktree.
- Build a baseline graph of the current code in scope, in parallel with E1. The prototype then writes only the differences.
- If the slice is larger than about 8 nodes, split it by file ownership, one agent per group. The orchestrator pins the shared interfaces in one file first. An agent proposes changes there and never changes an interface alone.
- Done when: every requirement has at least one concrete example, and the interfaces between groups are listed.

**E3 — Code-free design review.** Goal: no open finding of MAJOR, HIGH or worse on the design.
- An architect and a security reviewer work in parallel on the graph, the requirements and the callers.
- The orchestrator rules on every proposal and writes the rulings to a file. Prefer removing a feature over guarding it.
- One agent corrects the design with targeted edits, never a file rewrite.
- Done when: a round returns PASS or PASS-WITH-NOTES. Minor findings left at that point go to E4 as addenda instead of another round.

**E4 — Build ∥ test design.** Goal: the code implements the approved graph, and independent tests prove it.
- Implementers work by file ownership and do not write tests. Testers split the same way: one per file group, working from its graph examples, plus one for the cross-group ATs. Each writes its test cases first, then the tests, and proves them RED on base.
- A test verifies a case only if it asserts the case's expected result; running the code is not enough. A test counts as full only when the product itself produces what it asserts; text echoed by a stand-in, a CSS class in place of the painted style, a fixture that already shows the result before the trigger, or an entry point no product route calls make it partial.
- An implementer who cannot follow the graph writes the deviation down. A test or code that disagrees with a requirement is a finding; the code's text never replaces the requirement's.
- One integration step brings the work together to GREEN and applies the orchestrator's rulings on the interfaces.
- Done when: the tests are GREEN on the tree and RED on base for behavioural reasons, and the mutant table lists the E1 negative controls to run.

**E5 — Validate the change.** Goal: the change is proven and reviewed. Regression belongs to the batch end.
- Run the tests of the new and modified requirements, the tests the increment changed, and the repository's law guards: the project-wide tests that scan all source (style, copy and voice, markup safety, key bindings), named in its `CLAUDE.md` or `AGENTS.md`. Everything else runs at the batch end.
- Run the mutant table in a copy of the tree, never in the worktree.
- A code reviewer and a security reviewer each tag every finding `impl` or `design-gap`; a `design-gap` fix also updates the requirement and the graph. A corrective pass handles the findings and a re-review checks only what was blocking, until it passes. A minor finding left open goes to the backlog.
- Someone who did not write the test cases re-checks their `full`/`partial` marks and coverage; on a pilot this audit changed 24 % of the cases.
- The increment owes its acceptance tests: black-box, through keys and dialogs.
- Done when: no MAJOR, HIGH or worse is open, every test case is `covered` or its status is ruled, real captures are taken if the UI changed, the validation record is written (`04-validation.md`, about one page: the verdict, each run with its result and evidence path, the mutant score, the review verdicts and what was not run), and `trace_check.py` passes on the increment.

**Batch end.** Goal: the batch is whole and the operator can judge it.
- Run the full test suite once, in sequential chunks. A failure gets a corrective pass, RED first, recorded with its cause, its requirement and the files it changed; a law guard is never weakened to pass.
- Fold the batch's requirements into the project's requirements canon (`REQUIREMENTS.md`, in the form it already uses).
- Build one review page for the operator: captures, a change map, what they must know, and a decision form.
- Push only on approval. Then compare the remote CI's failing tests with the previous run's; a local green run is not the CI's verdict.
- Done when: the suite is GREEN or each failure is ruled, `trace_check.py` passes on the whole batch with the correction record (`--fixes`) and the canon (`--canon`), and the operator has decided.

## Running it

- **Operator gates.** The operator approves the increment list and rules on prototype rounds at E0, and decides at the batch end. Between those, run the increments through; stop only for a decision that is the operator's to make.
- **Who conducts.** The main session conducts every stage itself: it launches the stage's agents and reads their reports. Never hand a whole increment to one conductor agent: its context fills mid-increment, and its children keep running after it hands back.
- **Models.** The strongest model (Opus class) designs E1–E3, reviews, integrates and corrects. E4 implementation from the approved graph and mechanical work (mutant runs, records, captures, timing) go to a Sonnet-class model — Sonnet, DeepSeek v4 Pro, Kimi K2.7 or K2.8 — always behind an independent tester or reviewer. Log each stage's model in `steps.log`; when a model's work costs an extra pass or loses content, move that task up a class.
- **No stale writers.** Parallel agents own disjoint files. Before launching an agent into a worktree, confirm no earlier agent or process is still writing there; when an agent hands back mid-stage, stop its children and background jobs first. Judge an agent finished by its process or the harness notice, never by its log.
- **Background jobs.** Give every headless agent a timeout and a closed stdin (an open stdin can block it forever), and watch every long job for stalls.
- **Import trap.** With an editable install, `python -m pytest` imports from the cwd first. Run RED with the base tree as cwd and GREEN with the worktree, and print the package's `__file__` at the top of every transcript.
- **No changes mid-run.** Do not change source or scope while a long run is going.
- **Evidence in git.** Force-add evidence that `.gitignore` excludes (`*.log`).
- **Timing.** Log every stage's start and end in `steps.log`, and measure every increment with the same timing script.
